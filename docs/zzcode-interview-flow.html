一条主线记忆

先记住六个动词，再往每一步挂代码模块。

  1. 装配

    CLI 解析参数，构建 Workspace、Provider Client 和 Session。

  2. 感知

    ContextManager 组装并压缩 Prompt，当前请求永远保留。

  3. 决策

    模型只返回一个工具调用或最终答案，Runtime 统一解析。

  4. 行动

    工具经过校验、防重复、审批和 Diff 后才真正执行。

  5. 沉淀

    结果进入 History、Memory、TaskState、Trace 与 Checkpoint。

  6. 恢复 / 评测

    检测状态漂移，并用固定任务与消融实验验证设计。

60 秒面试复述

ZZCode 是一个运行在本地代码仓库里的轻量 Coding Agent。CLI 先完成模型、工作区和 Session 的装配，真正的核心是 ZZCode.ask() 控制循环：每轮由 ContextManager 把工作区信息、分层记忆、历史和当前请求组成 Prompt，模型再返回工具调用或最终答案。工具调用不会直接执行，而是统一经过白名单、参数校验、防重复、审批、路径隔离和结果 Diff。执行结果会回写 History 与 Working Memory，并持续生成 TaskState、Trace 和 Checkpoint，因此系统既能解释每一步，也能在恢复时检测文件过期或工作区漂移。最后项目通过固定 Harness 和 Context、Memory、Recovery 消融实验验证 runtime 合同与各模块收益。

高频追问

为什么不是纯聊天机器人？

它在真实仓库中运行，通过受约束的工具循环读取、修改、执行并验证工程任务。

如何控制上下文成本？

稳定 Prefix 可缓存；Memory、Relevant Memory 和 History 有独立预算并按优先级压缩；当前请求不裁剪。

如何避免重复读文件？

读取结果会生成文件摘要和 episodic note，后续按请求召回；写入后旧摘要立即失效。

如何保证恢复可靠？

Checkpoint 同时保存关键文件 freshness、workspace fingerprint 和 runtime identity，恢复时不盲信旧摘要。

工具安全如何实现？

显式白名单、严格参数校验、workspace 路径隔离、风险审批、Shell 环境 allowlist，以及 Trace / Report 脱敏。

如何证明这些设计有效？

Harness 验证 runtime 合同，Context、Memory、Recovery 消融分别验证压缩收益、重复读取降低和漂移检测。

模块详细拆解

每个模块按“职责、输入输出、关键机制、取舍、面试表达”展开。

01CLI 与依赖装配zzcode/cli.pyComposition Root

把命令行参数和环境变量翻译成 Runtime 所需的对象图，one-shot 与 REPL 最终统一进入 agent.ask()。

输入 / 输出

输入是 argparse 参数；输出是装配完成的新建或恢复后的 ZZCode 实例。

关键装配

  • Secret 名单与审批策略
  • WorkspaceContext 与 SessionStore
  • Ollama / OpenAI / Anthropic Client
  • max_steps 与 max_new_tokens

设计取舍

CLI 只处理配置和生命周期，不承载 Agent 推理，使交互界面、模型后端和核心循环彼此解耦。

容易被追问

--resume latest 从本地 Session 目录恢复；模型优先级为显式参数、环境变量、默认值。

面试回答

“CLI 是项目的 Composition Root，负责依赖注入和生命周期管理，所有业务行为最终收口到同一个 Runtime。”

02工作区快照zzcode/workspace.pyLazy Inspection

在第一次工具调用前提供一份小而稳定的仓库导航包，避免预加载整个代码库。

采集内容

repo root、分支、默认分支、Git status、最近 5 条提交，以及 AGENTS / README / pyproject / package.json 摘要。

Fingerprint

对结构化快照做 SHA-256；状态变化时刷新 Prompt Prefix，并影响恢复时的 Runtime Identity 判断。

为什么不全量索引

降低启动成本和上下文噪声。源文件仍通过 list/read/search 按需探索，符合本地 Agent 的渐进式感知。

边界

Fingerprint 不是整个仓库内容哈希；近期关键文件的内容变化由 Memory freshness 单独补足。

面试回答

“WorkspaceContext 提供稳定基线上下文，项目采用 lazy inspection，而不是启动时构建昂贵的全仓索引。”

03模型适配层zzcode/models.pyAdapter Pattern

隔离 Provider 的协议差异，Runtime 只依赖统一的 complete(prompt) 合同。

统一接口

输入 Prompt 和生成预算，输出文本；usage、cache 等附加信息通过 last_completion_metadata 返回。

协议差异

  • Ollama 本地生成接口
  • OpenAI-compatible JSON / SSE
  • Anthropic-compatible Messages
  • FakeModelClient 确定性测试

可靠性

网络错误和 5xx 有有限重试；非 JSON、错误响应和空文本被转换为明确 RuntimeError。

设计边界

这是最小公分母式 Adapter，不抽象所有 Provider 特有能力；Prompt Cache 也只在客户端明确支持时启用。

面试回答

“模型层保持窄接口，既方便切换 Provider，也让 Fake Client 能复用同一 Runtime 做确定性回归。”

04Runtime 控制循环zzcode/runtime.pySystem Orchestrator

ZZCode.ask() 是系统中枢：模型只做下一步决策，平台掌握上下文、工具、安全、状态、持久化和停止条件。

一轮生命周期

记录请求 → 创建 TaskState / Run → 构建 Prompt → 调模型 → 解析 Tool / Final / Retry → 执行或结束。

循环预算

tool_steps 统计工具执行；attempts 统计模型请求。额外的 max_attempts 防止 malformed output 无限重试。

模型协议

支持 JSON Tool 与适合多行文件的 XML Tool；有效 Final、工具调用和 Retry 都有明确分支。

可恢复推进

工具执行、上下文压缩、恢复异常和运行结束均创建 Checkpoint；命中上限时也保存可继续状态。

面试回答

“它是显式状态机式的 ReAct 循环：感知、决策、行动、记录。模型不直接拥有执行权，平台负责所有确定性约束。”

05上下文管理zzcode/context_manager.pyPrompt Orchestration

把不断膨胀的会话压缩成可控 Prompt，同时保留当前决策最需要的信息。

五段 Prompt

Prefix → Memory → Relevant Memory → History → Current Request。最新请求放最后且永不裁剪。

预算策略

总预算默认 12000 字符。超限依次压缩相关记忆、历史、工作记忆、稳定前缀，并为每区保留 floor。

历史语义压缩

优先保留最近 6 条；合并较早的重复读取；复用新鲜文件摘要；旧 Shell 和工具输出转成短摘要。

可观测性与边界

Metadata 记录每区压缩前后长度。当前按字符而非精确 Token 预算，简单且 Provider 无关，但存在估算误差。

面试回答

“不是粗暴截断，而是分区预算、优先级压缩和历史语义去重；核心不变量是当前用户请求完整保留。”

06分层记忆zzcode/memory.pyWorking / Episodic / Durable

History 保存完整事件，Memory 保存小而可复用的知识，两者分工不同。

Working Memory

当前任务、最近 8 个文件、最多 6 个新鲜摘要，用于每轮 Prompt 的轻量状态仪表盘。

Episodic / Durable

Episodic 最多 12 条跨轮笔记；Durable 持久化项目约定、决策、依赖事实和用户偏好。

Freshness

文件摘要带 SHA-256。读文件生成摘要，写或 Patch 立即失效；恢复时内容变化也会清理旧摘要。

召回与边界

按 tag、关键词重叠、时间排序，透明且低成本；不使用 Embedding，因此同义语义召回能力有限。

长期记忆防污染

必须有用户保存意图和固定语义前缀；Secret、临时任务状态、超长噪声不会晋升。

面试回答

“分层记忆的重点不是记得越多越好，而是控制生命周期，并用 freshness 防止代码变化后继续相信过期事实。”

07工具与安全边界zzcode/tools.py + run_tool()Execution Gateway

模型不能直接调用底层函数，所有外部动作都必须通过唯一工具总闸口。

执行流水线

Registry 存在性 → 参数校验 → 路径隔离 → 防重复 → 风险审批 → 执行 → 工作区 Diff → 状态分类。

工具能力

list/read/search、shell/write/patch，以及只读、限步数、限深度的 delegate 子 Agent。

安全细节

阻止 ../ 与符号链接逃逸；Shell 最长 120 秒；环境变量 allowlist；Secret 在 Trace 和 Report 中脱敏。

部分成功

Shell 非零退出但工作区已变化时标记 partial_success，保留 affected paths，提醒下一轮先检查 Diff。

边界

这些是应用层护栏，不等价于容器或系统调用级 OS 沙箱；更高风险场景还需要进程隔离。

面试回答

“安全不是写在 Prompt 里的建议，而是执行前后由平台强制实施的验证、授权、隔离和审计链路。”

08TaskState 状态机zzcode/task_state.pyRun Contract

用结构化状态回答一次请求进行到哪里、调用了多少次模型和工具、最终为什么停止。

核心字段

run_id、task_id、status、tool_steps、attempts、last_tool、stop_reason、final_answer、checkpoint_id、resume_status。

状态语义

running / completed / stopped / failed；状态与停止原因分离，便于区分“结果是什么”和“为什么停”。

数据流向

每轮写入 task_state.json，最终嵌入 report，同时被 Benchmark 用于预算与 Stop Reason 判定。

设计价值

避免从自然语言日志反推运行状态，为恢复、观测和评测提供稳定数据合同。

面试回答

“TaskState 是一次 ask 的最小状态机快照，连接在线控制循环和离线分析。”

09Session、Checkpoint 与 RunStoreruntime.py + run_store.pyRecovery & Audit

把“下次继续工作需要的状态”和“这一次运行发生过什么的证据”分开保存。

Session

保存跨轮 History、Memory、Checkpoint 和 Runtime Identity；整份 JSON 面向恢复。

Run Artifacts

task_state 原子写；trace.jsonl 逐事件追加；report.json 在结束时汇总结果与指标。

恢复判定

full-valid、partial-stale、workspace-mismatch、schema-mismatch；旧摘要失效时主动重锚定。

Runtime Identity

比较 cwd、模型、审批、Feature Flags、Workspace Fingerprint、Tool Signature 等，避免换运行环境后盲目续跑。

面试回答

“Session 面向继续工作，Trace / Report 面向解释与审计，Checkpoint 是两者之间的恢复锚点。”

10Evaluator 与 Metricszzcode/evaluator.py + zzcode/metrics.pyEvidence Layer

把“看起来能运行”转成可复现的成功定义、回归任务和模块消融证据。

Harness

校验任务 Schema；复制全新 fixture；独立运行 Agent；检查工件、Verifier、步数预算与 Stop Reason。

消融实验

Context 比较压缩；Memory 比较重复读取；Recovery 比较 stale / drift；Security 与 Provider 单独统计。

成功定义

工件存在、Verifier 通过、工具步数在预算内，并以 final_answer_returned 正常结束，四者缺一不可。

口径边界

Harness 证明 Runtime 合同，不证明模型上限。allowed_tools 当前被校验和记录，但没有动态裁剪 Registry。

面试回答

“我把确定性合同回归和模块消融分开，避免把 Harness、真实 Provider 表现和单模块收益混成一个结论。”

正常工具调用链

CLI → ask → ContextManager → Model → parse → run_tool → History / Memory → Trace / Checkpoint → 下一轮

最终回答链

Model Final → Session → TaskState completed → Durable Promotion → Final Checkpoint → Report → CLI

恢复链

--resume → SessionStore → Freshness / Identity 检查 → Prompt 注入恢复状态 → 重读关键文件 → 新 Checkpoint

3 分钟项目介绍模板

按“定位 → 主循环 → 上下文 → 记忆 → 安全恢复 → 证据”展开。

项目定位：ZZCode 是运行在本地代码仓库中的轻量 Coding Agent。项目重点不是简单调用大模型，而是实现模型外部的 Agent Runtime，使多步工程行为具备上下文控制、工具安全、状态恢复和审计能力。

核心链路：CLI 装配 Workspace、Provider、Session 和审批策略，统一进入 ZZCode.ask()。每轮由 ContextManager 构建 Prompt，模型返回 Tool Call 或 Final；Tool Call 必须经过统一的 run_tool 总闸口，校验、审批并执行后，结果写回 History 和 Memory，继续下一轮。

上下文与记忆：Prompt 分为 Prefix、Working Memory、Relevant Memory、History、Current Request。超限时按优先级压缩，当前请求不裁剪。记忆分 Working、Episodic、Durable 三层，文件摘要带内容哈希，修改后自动失效。

安全与恢复：工具通过白名单、参数校验、路径隔离、防重复、风险审批、Shell 环境 allowlist 和产物脱敏进行约束。Session 负责跨轮恢复，RunStore 保存 TaskState、Trace 和 Report；Checkpoint 通过 freshness、Workspace Fingerprint 和 Runtime Identity 检测漂移。

验证结果：12 个 Harness 任务的通过率、预算内完成率和 Verifier 通过率均为 100%；Context 平均压缩 16.19%，当前请求保留率 100%；Memory On / Off 重复读取为 0 / 60；Workspace Drift Detection 为 100%，Resume False Accept 为 0%。这些结果证明 Runtime 合同和模块收益，不代表模型能力上限。
